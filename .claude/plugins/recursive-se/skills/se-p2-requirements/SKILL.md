# P2 — Requirements

> 本阶段唯一核心问题：**当前 SoI 必须具备什么可验证的能力和性质？**
> 只定义"必须做到什么 + 怎么判满足"。**验证标准在此定义，执行在 P7。**

## 五问

### P2-Q1 必须提供什么功能能力？

按能力分组（服务 P1 的场景编号），每条：
`REQ-<组>-<序号>：[一句话能力，动词开头]`
要求：每条能回引它服务的场景（C1/C2/…）——**无场景来源的需求要么补场景要么删**。

### P2-Q2 能力必须达到什么性能或质量水平？

每条功能需求补质量维度（如适用）：性能/容量/可靠性/可恢复性/安全边际。
模板：`在 [条件] 下达到 [量化水平]`。**质量需求必须量化或给出可判定的判定规则。**

### P2-Q3 必须满足哪些外部接口要求？

与 P1-Q2 边界上的外部实体交互：协议/格式/时序/方向约束。

### P2-Q4 有哪些不可违反的外部约束？

法规/标准/组织策略/物理定律/预算工期等硬约束（不可协商的才放这里）。

### P2-Q5 如何判定每条 Requirement 被满足？

**每条 REQ 必须挂验证标准**（这是本阶段最重要的产出）：
```
REQ-xxx:
  Capability: ...
  Criterion: [可操作的判定方法——测试/分析/演示/审查 四选一或组合]
```
要求：写不出 Criterion 的 REQ 不是需求，是愿望——改写或删除。

## 输出规范

写入 `docs/SE/<soi-name>/P2-requirements.md`：REQ 台账表（REQ / 能力 / Criterion / 状态 ✅🟡❌ / 服务场景）。状态列在 P7 回填证据时更新。

## Exit Gate

每条 REQ 可验证（有 Criterion）？每条可回引场景或约束？无方案词汇泄漏？质量需求量化？
