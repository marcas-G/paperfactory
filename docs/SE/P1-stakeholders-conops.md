# P1 — Stakeholder & Operational Concept

> 阶段唯一问题：**谁会怎样使用系统，系统处于什么外部环境？**

## P1-Q1 Stakeholder 清单

| 角色 | Concern（关切） | 影响/被影响 |
|---|---|---|
| **S1 研究人员（主用户）** | 研究进度不丢、结论可追证、少做重复劳动 | 使用全部功能；最终价值裁决者 |
| **S2 研究合作者/导师** | 看懂研究过程与依据，审查结论可靠性 | 只读消费者：读报告、审计证据链 |
| **S3 系统开发者（我们自己/贡献者）** | 架构可维护、分层纪律可执行、规格可验证 | 维护者；架构测试与 SE 基线的使用者 |
| **S4 未来端开发者（移动/桌面）** | 协议稳定、接入成本低 | 只依赖 PROTOCOL.md + 生成 SDK |
| **S5 LLM/算力供应商（外部）** | — | 外部依赖：模型质量与可用性影响系统 |

## P1-Q2 运行环境

```text
- 单机部署（当前）：笔记本/工作站上的 Node 进程 + SQLite + 可选 Python 科学微服务
- 网络：能访问 LLM 网关与公开学术 API（arXiv/Semantic Scholar）；
  断网时系统应可启动并服务历史数据，新研究能力受限
- 外部系统：LLM 网关（OpenAI 兼容协议）、学术 API、（可选）PostgreSQL
- 干扰因素：LLM 网关不稳定（限流/断线/证书问题——已实测遭遇）、
  学术 API 限流、进程意外退出、机器重启
```

## P1-Q3 操作概念（ConOps）——三条主场景

### C1 日常研究循环（S1 高频）

```text
1. 研究员在 web/tui 输入研究问题，发起一次研究运行
2. 系统自主执行：检索真实文献 → 评估筛选 → 生成假设 → 设计并运行实验
   → 汇总证据 → 产出报告；全程事件流实时可见（阶段/工具/产物）
3. 关键阶段（manual 模式）弹出审批：人决定 放行/修改/拒绝
4. 完成后研究员阅读报告，点击引用核验文献，决定下一步问题
5. 多次循环形成项目：状态（问题/假设/证据）持续累积、可回看
```

### C2 中断恢复（S1 低频高价值）

```text
1. 数小时的研究任务进行中，进程退出（崩溃/关机/主动停止）
2. 研究员重启系统，打开同一项目
3. 已完成阶段的产物与结论原样在场，未完成阶段可重新发起
   （理想态：从断点续跑——见 P2 REQ-REC 系列）
```

### C3 审计追溯（S2/S1 低频）

```text
1. 报告中某结论被质疑
2. 打开项目，沿 结论→证据→实验→文献 的链路逐层下钻
3. 每层可见：内容、来源（可点开）、产生时间、当时的判定依据
```

## P1-Q4 非目标场景（与 P0 边界呼应）

```text
- 多人同时编辑同一研究状态（当前单用户；并发编辑不在 ConOps）
- 无 LLM 环境下的全自动研究（人的审批与提问始终在场）
- 移动端离线研究（移动端未来仅为查看与轻交互）
```

## P1 Exit Gate 自查

| 问 | 答 |
|---|---|
| 谁影响系统 | S1-S5 五类，S1 为主用户 |
| 使用环境 | 单机 Node+SQLite，外部依赖 LLM 网关/学术 API |
| 主场景 | C1 日常循环 / C2 中断恢复 / C3 审计追溯 |
| 明确不做的场景 | 多人并发编辑、无 LLM 全自动、移动离线 |
